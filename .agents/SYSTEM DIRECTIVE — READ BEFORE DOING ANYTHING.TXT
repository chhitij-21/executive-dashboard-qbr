SECTION 34 — ARCHITECTURAL BLIND SPOT PROTOCOL
═══════════════════════════════════════════════════════════════

HONEST TRUTH (read this before you start):
  Your SELF-REVIEW catches implementation bugs, not architectural
  mistakes. If you pick the wrong DB, wrong auth model, wrong
  multi-tenancy strategy, wrong API shape — your self-review will
  return CLEAN because you don't know it's wrong. You cannot audit
  your own architecture. Only the human can.

Therefore: certain items are ARCHITECTURAL. For these, self-review
is NOT sufficient. They require human sign-off BEFORE you code and
AFTER you finish.

A. WHICH ITEMS ARE ARCHITECTURAL (hard-coded list)
   #2  Storage (S3 / R2 / Supabase / disk)
   #3  Database (Postgres / SQLite / Mongo / Prisma / raw pg)
   #4  Auth (JWT / session / OAuth / library choice)
   #8  Multi-tenancy (schema-per-tenant / row-level / separate DBs)
   #10 Job queue (BullMQ / pg-boss / SQS / cron)
   #11 Template versioning (file / DB / git)
   #14 API versioning (/v1 / headers / date-based)
   #19 Connectors (webhook / poll / OAuth-per-integration)

   Any item NOT on this list is IMPLEMENTATION — self-review is
   sufficient. Any item that TURNS OUT to require an architectural
   choice mid-way must be re-classified and stopped immediately.

B. BEFORE CODING an architectural item
   Do NOT propose a single plan. Propose 2–3 options:

     ARCHITECTURAL DECISION REQUIRED — item #<n>
     Option A: <name> — how it works in 2 lines
       Pros: <2 bullets>
       Cons: <2 bullets>
       Reversibility: EASY / HARD / ONE-WAY
       Cost if wrong: <what breaks, what migration needed>
     Option B: <name> — ...
     Option C: <name> — ...

     My recommendation: <A/B/C> — because <1 line>
     What I am NOT qualified to judge: <e.g., your team's SQL
     familiarity, your compliance requirements, your cloud spend
     ceiling>

     Reply with: "choose A" / "choose B" / "choose C" / "more info on X"

   Wait for my choice. Do NOT proceed with a default. Do NOT start
   coding "while waiting". Do NOT pick the option you like best and
   pretend it was my choice.

C. AFTER CODING an architectural item
   Even if SELF-REVIEW returns CLEAN, you must emit:

     ITEM #<n> — AWAITING ARCHITECTURAL REVIEW
     (do NOT mark as DONE, do NOT say "complete")

     Self-review result: CLEAN (implementation)
     Architectural review: NOT PERFORMED — I cannot audit my own
       architecture. Human MUST read the full diff.

     Full diff for human: git show <sha>
     What to scrutinize:
       - <3-5 specific lines/decisions the human should look at>
       - <what tradeoff was made at each>
       - <what would need to change if this proves wrong>

     Questions only the human can answer:
       - <e.g., "does your team have Postgres experience?">
       - <e.g., "is row-level tenant isolation compliant for your
          auditors?">

     Status: CODE-READY / AWAITING HUMAN ARCHITECTURAL REVIEW

   Only after the human replies "architectural review passed" may
   this item be counted toward wave completion.

D. REVERSIBILITY DISCLOSURE (mandatory)
   For every architectural item, before finalising, print:

     REVERSIBILITY: <EASY / HARD / ONE-WAY>
     If we later change this choice:
       - What migrations are needed: <list>
       - Downtime: <estimate>
       - Data loss risk: <yes/no + what>
       - Estimated effort to reverse: <hours/days/weeks>

   Examples of ONE-WAY (flag loudly):
     - Choosing Postgres vs Mongo (data model differs)
     - JWT vs session (stateless vs stateful — auth flow rewrite)
     - Row-level vs schema-per-tenant (migration is painful)

E. WHEN AN ARCHITECTURAL ITEM GOES WRONG
   If, after human review, the choice is rejected:
     - Do NOT argue. Do NOT defend the choice.
     - Immediately produce a REVERSAL PLAN: what to un-build,
       what to build instead, what the migration path is.
     - Treat the reversal as a new sub-item #<n>.revert.

F. HARD RULES
   F1. Never mark an architectural item DONE. Only "AWAITING
       ARCHITECTURAL REVIEW" then, after human passes it, "DONE".
   F2. Never present only one option for an architectural item.
       Minimum 2 options + reversibility rating.
   F3. Never skip the REVERSIBILITY block. If you don't know, say
       "UNKNOWN — needs research before choosing".
   F4. Never let SELF-REVIEW = architectural approval. They are
       different gates. Both must pass.
   F5. If the human is unavailable and you must proceed to keep
       the wave moving, pick the most reversible option and tag
       it: PROVISIONAL CHOICE — reversed in <10 min if rejected.
       Mark status = PROVISIONAL, not DONE.
